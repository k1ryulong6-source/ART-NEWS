## 初步结论

**暂停整体授权（License gate blocked）。** 当前公开仓库未找到根目录 LICENSE/COPYING，原创代码可作为候选开源内容，但媒体原文、译文、来源配图、字体、依赖、生成物与内部台账必须区分。版权无法仅通过开源许可证解决。

## 建议的授权结构（仅供维护者决定）

1. **软件**：若所有纳入许可的代码权属与兼容性确认无问题，考虑将 MIT（简单复用）或 Apache-2.0（含明确专利条款）作为自有软件许可证；选择前核第三方片段和贡献权。
2. **数据和新闻**：单独写 `CONTENT_RIGHTS.md` 或 `LICENSE_SCOPE.md`，明确不对第三方新闻、照片、转载段落、受限翻译、外部数据库作超越自身权利的再授权。可为**明确原创且具有完整权利**的独立数据制定另外许可。
3. **字体**：保留现有 SIL OFL 文本和对应溯源信息；不受前述软件许可证覆盖。
4. **软件依赖**：保留上游权利和NOTICE/许可证文本的履行路径；建立可更新的版本/来源/许可台账。
5. **对外分发**：明确“仓库克隆、静态 Pages 包、Docker 镜像、线上阅读”是不同分发面，各自核授权。媒体来源对自动下载和再发布的条款需逐来源审查；没有明确许可不要将公开可访问等同于可以完整复制。

- [ ] P0 盘点 `data/live.json`、`data/translation-input/`、`data/translations/`、`frontend/data.js` 是否包含受限正文、译文、受保护图片或需要移出再分发产物的部分。

- [ ] P0 公开仓库现有内容已经具有外部可见性；不得以为删除 HEAD 文件就能自动从所有历史 commits / fork / archive 消失，须另做 Git 历史审核。
- [ ] P1 查验原创代码作者、AI 辅助贡献与第三方代码复制情况，选定代码许可证并明确软件/新闻/图片/字体例外范围。
- [ ] P1 核查软件包直接/间接依赖及可下载模型权重（若实际随项目发布）。
- [ ] P2 审核字体子集/Logo/截图及分发通知文本。
- [ ] P2 将权属检查纳入构建/CI，确保未经批准的正文不自动打入开源发布包。
- [ ] 最后由项目维护者决定是否合并许可与分发政策；视实际法律争议咨询熟悉新闻著作权和跨境再分发的专业律师。

## 申请 Codex for OSS 的影响

不能将“代码公开可看”直接称作“拥有完整开源许可证的可复用项目”。在完成至少代码许可与第三方内容边界说明后，再准确说明项目贡献。权益申请与任何版权使用权限都互不替代。
